# Glossary

## Core Terms

### Greenfield Development
Building a software system from scratch with no existing code, infrastructure, or constraints. Named after undeveloped "green" land with no existing structures.

### Brownfield Development
Developing within, on top of, or alongside existing software systems that are already in production. Named after previously developed "brown" land that may have existing structures or contamination.

### Legacy System
An older system that remains in use, often because it performs critical business functions, even though it may use outdated technology. Not inherently negative — it means the system has provided value long enough to become established.

### Technical Debt
The implied cost of rework caused by choosing quick/easy solutions over better approaches that would take longer. Like financial debt, it accumulates interest over time.

---

## Architecture Terms

### Monolith
A software application where all components are combined into a single program, deployed as one unit. Common in brownfield systems built before microservices became popular.

### Microservices
An architectural style where an application is structured as a collection of small, independent services that communicate over APIs. Each service can be developed, deployed, and scaled independently.

### Cloud-Native
Applications designed specifically to exploit cloud computing advantages: elastic scaling, managed services, containers, and distributed systems from the ground up.

### Serverless
A cloud execution model where the cloud provider manages server infrastructure. Developers write functions that run on demand without managing servers. Common in greenfield projects.

### Event-Driven Architecture
A software architecture pattern that uses events (state changes) to trigger and communicate between decoupled services. Key enabler for modernization.

---

## Modernization Terms

### Strangler Fig Pattern
A modernization approach where new functionality is built alongside the old system, gradually "strangling" it by routing traffic to the new system piece by piece until the old system can be decommissioned.

### Anti-Corruption Layer (ACL)
A translation layer between new (clean) code and legacy (messy) code that prevents legacy complexity from leaking into the new system's domain model.

### Branch by Abstraction
A technique for making large-scale changes to a software system gradually by creating an abstraction layer, building an alternative implementation behind it, and switching over using feature flags.

### Lift and Shift (Rehosting)
Moving an application to the cloud exactly as-is, without modification. The fastest but least beneficial cloud migration strategy.

### Replatforming
Moving to the cloud with minor optimizations (e.g., switching to managed databases) without fundamentally changing the application architecture.

### Refactoring
Restructuring existing code without changing its external behavior. In modernization context, often means redesigning for cloud-native patterns.

---

## Development Terms

### CI/CD (Continuous Integration / Continuous Deployment)
Automated pipelines that build, test, and deploy code changes. Essential for both greenfield (fast iteration) and brownfield (safe changes).

### Feature Flags (Feature Toggles)
A technique that allows enabling/disabling features at runtime without deploying new code. Critical for gradual rollouts and brownfield migrations.

### Characterization Tests
Tests written to document the existing behavior of a system before making changes. Used in brownfield development to ensure modifications don't break existing functionality.

### Domain-Driven Design (DDD)
An approach to software development that centers the project on the core business domain. Important for both defining greenfield architecture and identifying brownfield bounded contexts.

### Bounded Context
A DDD concept that defines clear boundaries within which a particular domain model applies. Useful for decomposing monoliths into microservices.

---

## Business Terms

### Digital Transformation
The process of using digital technologies to create or modify existing business processes, culture, and customer experiences. Drives most greenfield/brownfield decisions.

### Total Cost of Ownership (TCO)
The complete cost of a system over its lifetime, including development, hosting, maintenance, licensing, training, and eventual decommissioning.

### Return on Investment (ROI)
The financial return generated by an investment relative to its cost. Greenfield typically has longer ROI timeline; brownfield offers faster returns.

### Vendor Lock-in
Dependency on a specific vendor's technology, making it difficult or expensive to switch. Affects both greenfield (choice of cloud provider) and brownfield (existing vendor contracts).

### Technical Bankruptcy
When the accumulated technical debt in a system becomes so large that incremental improvement is no longer viable, forcing a write-off and rebuild (greenfield).

---

## Cloud Migration Terms (The 7 Rs)

| Term | Definition |
|------|-----------|
| **Rehost** | Move to cloud as-is (lift & shift) |
| **Replatform** | Minor cloud optimizations during migration |
| **Refactor** | Redesign application for cloud-native |
| **Repurchase** | Replace with commercial SaaS product |
| **Retire** | Decommission the application |
| **Retain** | Keep as-is, don't migrate |
| **Rebuild** | Complete greenfield rewrite |

## Organizational Terms

### Conway's Law
"Organizations design systems that mirror their own communication structure." Important when deciding architecture — your team structure will influence whether greenfield or brownfield succeeds.

### Platform Team
A team that provides shared tools, services, and infrastructure for product teams. Common in organizations managing both greenfield and brownfield simultaneously.

### Two-Pizza Team
A team small enough to be fed by two pizzas (typically 6-8 people). Amazon's model for microservices ownership — each team owns one or more services independently.

### SRE (Site Reliability Engineering)
Engineering discipline focused on reliability of production systems. Critical in brownfield environments where stability must be maintained during modernization.

---

## Metrics and Assessment Terms

### DORA Metrics
DevOps Research and Assessment metrics for software delivery performance:
- **Deployment Frequency**: How often code is deployed to production
- **Lead Time for Changes**: Time from commit to production
- **Change Failure Rate**: Percentage of deployments causing failures
- **Time to Restore Service**: How quickly failures are resolved

### Fitness Functions
Automated metrics that evaluate how well a system meets its architectural requirements over time. Used to ensure brownfield modernization stays on track.

### Architecture Decision Records (ADRs)
Lightweight documents capturing important architectural decisions, their context, and consequences. Critical for both greenfield (documenting new decisions) and brownfield (understanding past decisions).
